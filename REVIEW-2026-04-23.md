## [CRITICAL] Issues

### CR-01 — amountCents client-side non vérifié contre le quote Guesty

**Fichier :** `src/app/api/guesty/reservation/route.ts:37,76,104,153`

**Issue :** `amountCents` est un champ du body envoyé par le client (`z.number().int().positive()`). Il est formaté pour affichage et stocké dans Supabase sans jamais être comparé au montant réel du quote Guesty créé côté serveur. Un attaquant peut envoyer `amountCents: 1` et la réservation sera créée avec ce montant dans la base. Le vrai montant débité est celui que Guesty charge sur la carte, mais la ligne Supabase sera corrompue — ce qui fausse les emails de remboursement, la politique d'annulation et tout reporting.

**Impact :** Données financières corrompues. Le montant affiché dans les emails et utilisé dans `calculateRefundAmountCents` sera le montant truqué.

**Fix :** Ne pas accepter `amountCents` du client. Récupérer le quote côté serveur via `quoteId + ratePlanId` et calculer le montant depuis la réponse Guesty.

```typescript
// Dans reservation/route.ts : supprimer amountCents du schema
// et calculer depuis le quote déjà créé (le client passe quoteId+ratePlanId)
const quote = await guestyClient.getQuote(data.quoteId) // si l'endpoint existe
// ou recréer depuis les params si nécessaire
const amountCents = Math.round(
  quote.rates.ratePlans
    .find(rp => rp.ratePlan._id === data.ratePlanId)
    ?.ratePlan.money.subTotalPrice * 100 ?? 0
)
```

### CR-02 — Email d'annulation non envoyé quand refund > 0

**Fichier :** `src/app/api/reservations/cancel/route.ts:54-68`

**Issue :** La logique envoie l'email d'annulation uniquement dans le bloc `else` (quand `refundAmountCents === 0`). Quand un remboursement est dû, l'appel `refundReservationPayment` est fait mais aucun email n'est envoyé au voyageur. Le voyageur est annulé sans notification.

```typescript
if (refundAmountCents > 0) {
  // ...
  await guestyOpenApi.refundReservationPayment(...)
  // BUG : pas d'email ici
} else {
  await sendCancellationEmail(inquiry, null) // envoyé seulement si pas de remboursement
}
```

L'email dans le cas remboursement est supposé arriver via le webhook `payments.refunded` — mais si le webhook est en retard ou rate l'événement, le voyageur ne reçoit rien. C'est un bug fonctionnel certain : le chemin non-refund envoie l'email immédiatement, le chemin refund espère un webhook secondaire.

**Impact :** Silence total pour le voyageur après annulation avec remboursement. UX cassée, risque de litige.

**Fix :** Envoyer l'email dans les deux branches, avec le montant de remboursement en paramètre :

```typescript
if (refundAmountCents > 0) {
  // ...
  await guestyOpenApi.refundReservationPayment(...)
  await sendCancellationEmail(inquiry, refundAmountCents)
} else {
  await sendCancellationEmail(inquiry, null)
}
```

### CR-03 — Token d'annulation non single-use (replay attack)

**Fichier :** `src/lib/cancel-token.ts`, `src/app/api/reservations/cancel/route.ts`

**Issue :** Un token d'annulation HMAC valide peut être rejoué indéfiniment pendant sa durée de vie (30 jours). La route `/api/reservations/cancel` vérifie que `inquiry.status` est `confirmed` ou `pending` avant d'annuler — ce qui protège partiellement. Mais si une réservation est ré-ouverte ou si le statut redevient éligible (edge case webhook), le même token peut annuler à nouveau.

Plus concrètement : rien n'empêche de rejouer le token 30 jours après annulation sur une nouvelle réservation du même `reservationId` (si Guesty recycle des IDs, ce qui n'est pas impossible).

**Impact :** Risque d'annulation non voulue par replay. Contrôlé partiellement par le check de statut, mais pas éliminé.

**Fix :** Marquer le token comme consommé en base au premier usage réussi :

```typescript
// Dans inquiries, ajouter : cancel_token_used_at: string | null
// Après updateInquiry({ status: 'canceled' }), marquer :
await updateInquiry(inquiry.id, {
  status: 'canceled',
  canceled_at: new Date().toISOString(),
  cancel_token_used_at: new Date().toISOString(),
})
// Et vérifier au début de la route :
if (inquiry.cancel_token_used_at) {
  return NextResponse.json({ error: 'token_already_used' }, { status: 409 })
}
```

### CR-04 — Webhook Guesty bypassable sans secret en production (faux négatif possible)

**Fichier :** `src/lib/guesty-webhook.ts:9-11`

**Issue :** Si `GUESTY_WEBHOOK_SECRET` est défini mais vide (`""`), la condition `if (!secret)` est vraie et le code retourne `process.env.NODE_ENV !== 'production'`. En production avec `GUESTY_WEBHOOK_SECRET=""` (variable présente mais vide), `!secret` est `true` → retourne `false` → OK, la vérification est refusée. C'est correct.

Mais le comportement inverse est plus subtil : la logique `return process.env.NODE_ENV !== 'production'` signifie qu'en staging ou preview (mode `development`/`test`), n'importe quelle requête POST vers le webhook est acceptée sans aucune vérification. Si l'URL de staging est exposée, un attaquant peut déclencher des confirmations ou annulations arbitraires.

**Impact :** En environnement non-production exposé publiquement (Vercel preview), n'importe qui peut déclencher des transitions de statut de réservation.

**Fix :** En absence de secret, rejeter systématiquement plutôt que de bypass :

```typescript
if (!secret) {
  // Ne jamais bypasser, même en dev. Logger un avertissement.
  console.error('[guesty-webhook] GUESTY_WEBHOOK_SECRET non configuré — requête rejetée')
  return false
}
```

### CR-05 — Pas de security headers HTTP dans next.config

**Fichier :** `next.config.ts`

**Issue :** Aucun header de sécurité configuré (`Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`). Le site charge des scripts tiers depuis S3 AWS (`guesty-search-widget.tsx:29,37`) sans CSP qui restreindrait les origines autorisées.

**Impact :** XSS amplifié si un script tiers est compromis. Clickjacking possible. Pas de protection MIME-sniffing.

**Fix :**

```typescript
const nextConfig: NextConfig = {
  async headers() {
    return [
      {
        source: '/(.*)',
        headers: [
          { key: 'X-Frame-Options', value: 'DENY' },
          { key: 'X-Content-Type-Options', value: 'nosniff' },
          { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
          {
            key: 'Content-Security-Policy',
            value: [
              "default-src 'self'",
              "script-src 'self' 'unsafe-inline' https://s3.amazonaws.com",
              "style-src 'self' 'unsafe-inline' https://s3.amazonaws.com",
              "connect-src 'self' https://*.guesty.com https://*.stripe.com",
              "frame-src https://js.stripe.com",
            ].join('; '),
          },
        ],
      },
    ]
  },
  // ...
}
```

### WR-02 — checkIn >= checkOut non validé dans les routes API

**Fichier :** `src/app/api/guesty/quote/route.ts:8-9`, `src/app/api/guesty/reservation/route.ts:34-35`

**Issue :** La validation Zod vérifie que `checkIn` et `checkOut` sont des dates ISO valides, mais ne vérifie pas que `checkOut > checkIn`. Un body avec `checkIn: "2026-06-10"` et `checkOut: "2026-06-05"` passe la validation et est transmis à Guesty (qui renverra probablement une erreur, mais ça n'est pas garanti).

**Impact :** Quotes et réservations potentiellement malformées envoyées à Guesty.

**Fix :**

```typescript
const schema = z.object({
  checkIn: z.iso.date(),
  checkOut: z.iso.date(),
  // ...
}).refine(
  (data) => data.checkOut > data.checkIn,
  { message: 'checkOut doit être postérieur à checkIn', path: ['checkOut'] }
)
```

### WR-03 — Assertions `as unknown as typeof data.policy` non documentées

### WR-05 — `globalThis as unknown` pour le token cache Guesty (race condition potentielle)

**Fichiers :** `src/lib/guesty-client.ts:18-22`, `src/lib/guesty-openapi.ts:4-7`

**Issue :** Les deux clients OAuth utilisent `globalThis` comme cache mémoire pour les tokens. En environnement serverless avec plusieurs instances concurrentes (Vercel Edge ou Lambda cold starts multiples), deux requêtes simultanées peuvent déclencher deux appels OAuth en parallèle, écrire des tokens différents et créer une condition de course.

**Impact :** Requêtes OAuth redondantes, possible dépassement de rate limit Guesty en pic.

**Fix :** Mettre en place un mutex simple ou utiliser Supabase (déjà en place dans `guesty-oauth-cache.ts`) comme source de vérité unique, et supprimer le cache `globalThis` pour `guesty-openapi.ts` (qui n'a pas de layer Supabase comme `guesty-client.ts`).

### WR-06 — `isDarkBg` dans custom-cursor : parsing RGB fragile + GetComputedStyle en boucle

**Fichier :** `src/components/ui/custom-cursor.tsx:111-127`

**Issue :** `getEffectiveBg` remonte le DOM en appelant `getComputedStyle` à chaque niveau parent (potentiellement 10-15 niveaux). Ce pattern provoque du layout thrashing si appelé fréquemment. Le throttle à 80ms limite l'impact, mais un WeakMap par élément (pas par position de curseur) peut cache des valeurs incorrectes si l'élément change de fond dynamiquement.

`isDarkBg` parcourt la string RGB avec un regex et indexe `match.map(Number)` sans guard sur l'index 0 (le full match) — `[, r, g, b]` est correct en destructuring mais `match` peut retourner `null` si le format n'est pas `rgb(...)` (ex: `rgba`, `hsl`).

**Impact :** Potentiel `null` crash sur certains backgrounds CSS (`rgba`, `hsl`, `color-mix`).

**Fix :**

```typescript
function isDarkBg(bg: string): boolean {
  const match = bg.match(/rgb\((\d+),\s*(\d+),\s*(\d+)\)/)
  if (!match) return false
  const [, r, g, b] = match.map(Number)
  const luminance = (0.299 * r + 0.587 * g + 0.114 * b) / 255
  return luminance < 0.5
}
```

### WR-07 — Lenis : gsap.ticker non nettoyé dans le cleanup

**Fichier :** `src/components/providers/lenis-provider.tsx:30-38`

**Issue :** `gsap.ticker.add((time) => lenis.raf(time * 1000))` ajoute un ticker GSAP qui n't est jamais retiré dans le `return () => { ... }` du useEffect. Seul `lenis.destroy()` est appelé. Le ticker GSAP continue de s'exécuter après unmount et appelle `lenis.raf` sur une instance détruite.

**Impact :** Memory leak. Erreurs silencieuses en navigation (hot reload, transitions de page).

**Fix :**

```typescript
const ticker = (time: number) => lenis.raf(time * 1000)
gsap.ticker.add(ticker)

return () => {
  gsap.ticker.remove(ticker)
  lenis.destroy()
  lenisRef.current = null
}
```
